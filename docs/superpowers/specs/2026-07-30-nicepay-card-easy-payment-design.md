# NICEPAY 카드·간편결제 1차 도입 설계

## 목표

기존 워크숍 신청 결제 흐름을 유지하면서 NICEPAY가 제공하는 기존 결제창 안에서 카드와 활성화된 간편결제(카카오페이, 네이버페이, 삼성페이)를 선택할 수 있게 한다.

## 범위

- 기존 `워크숍 신청하기` 버튼과 NICEPAY 결제창 호출 흐름을 유지한다.
- 별도의 IYOHOUSE 결제수단 선택 모달을 추가하지 않는다.
- NICEPAY의 카드·간편결제 선택 UI를 사용한다.
- 기존 pending 신청 생성, 서버 승인, 결제 금액 검증, 정원 확정, 성공·실패·취소 처리를 변경하지 않는다.
- NICEPAY 응답에 포함되는 실제 결제수단 정보는 기존 `payments.payment_method` 기록 흐름에서 보존한다.

## 제외 범위

- 가상계좌 발급, 입금대기 화면, 입금 웹훅 상태 전환
- 가상계좌용 Supabase migration 및 운영 웹훅 등록
- 결제 환불·부분취소 로직
- 워크숍 상세 UI, Sanity CMS, 정원 계산 로직 변경

## 처리 흐름

1. 사용자가 기존 방식으로 워크숍 일정과 가격을 선택한다.
2. 기존 서버 checkout API가 소유권·상태·금액을 검증한다.
3. 서버가 기존 NICEPAY payload를 생성한다.
4. 클라이언트가 기존 `AUTHNICE.requestPay()`를 호출한다.
5. NICEPAY 결제창에서 카드 또는 가맹점에 활성화된 간편결제를 선택한다.
6. 기존 return URL 승인 API가 인증 결과와 금액·주문번호를 검증한다.
7. 기존 확정 RPC가 신청과 결제를 확정한다.

간편결제별 별도 승인 API를 만들지 않고 NICEPAY의 공통 승인 응답을 사용한다. 실제 간편결제 수단 식별값이 제공되면 결제 원장에 기록하고, 제공되지 않는 경우에도 기존 카드 결제처럼 결제 확정 자체는 정상 처리한다.

## 운영 안전성

- 변경 전후 `method: "card"` 기반 결제 요청 계약을 유지한다.
- Supabase 스키마와 RPC를 변경하지 않는다.
- 운영 환경에서 NICEPAY 가맹점의 간편결제 활성화 상태를 확인한다.
- 테스트 결제에서 카드 1건과 간편결제 1건을 각각 승인·실패·취소 확인한다.
- 기존 카드 결제 회귀 테스트가 통과한 뒤 배포한다.

## 성공 기준

- NICEPAY 결제창에서 활성화된 간편결제 수단이 표시된다.
- 카드 결제는 기존과 동일하게 확정된다.
- 간편결제 결제도 동일한 신청·결제 원장·정원 확정 흐름을 통과한다.
- 결제 실패나 창 닫기 시 기존 pending 정리 동작이 유지된다.
- 가상계좌 관련 코드와 DB에는 변경이 없다.
